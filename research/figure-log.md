# 図版ログ(採用記録と判断メモ)

採用した図版について「なぜその構図にしたか」「プリセットからどう逸脱したか」を残す台帳。
**プロンプト全文は書かない**。全文は各 md の `::: details` 内に採用版が入っており、二重に持つとズレるため。

形式・運用ルールは `research/writing-guide.md` の「図版プレースホルダー」節を参照。

## 全図に効く教訓

図を作るたびに踏んだ罠をここに足していく。次の図を作る前に読む。

- **線の接続先は「どこから」を具体的に書く**。「3 つのボックスの中間から下へ」と書いたら、生成側が「真ん中のボックス(Part II)から」と解釈した(図 0-1 の 2 版目)。全体から 1 本ぶら下げる構図は誤解されやすい。**繋がない方が正確に伝わるならそもそも線を引かない**
- **線の禁止は 2 箇所に書く**。生成モデルは線を勝手に補完する。LAYOUT に `no connecting line` と書き、さらに ARROWS の末尾に `No other lines or connectors anywhere in the diagram.` を足すと通る
- **特定の要素だけを青で塗らない**。「1 つだけ青」は視覚的に「これが主役/ゴール」と読まれる。並列な要素は同じ塗りにし、青は矢印など「進行」に使う(CLAUDE.md の中立性ルールと直結する)
- **横一列に 6 要素以上を 3:2 に入れない**。文字が小さくなる。ワイド 2:1 プリセットを使う
- **装飾アイコン(警告三角形・稲妻)より言葉を置く**。「異常が起きた」ことは枠の色とタグで伝わる。図が足すべきは異常の**中身**(`not declared` / `same package.json`)。アイコンは要素が増えるだけで、プリセットの `simple geometric icons` からも外れる(図 3-3・4-1)
- **塗りは階層を、枠の色は状態を表す**。同じ階層の要素を 1 つだけベタ塗りにすると、階層が違うように見える。白背景+太い色枠なら「同格だが状態が違う」を表現できる(図 3-2 で確立。図 2-1 の MAJOR/MINOR も同じ形)

## 採用記録

### 図 0-1 この本の構成(2026-08-30 / 標準 3:2)

`docs/introduction.md` — Part I/II/III の 3 ボックス + Appendix。

初版は `Box 3 (blue, gem icon) labeled "pnpm"` で、pnpm だけが青塗り+宝石アイコンだった。「Basics → History を経てたどり着く宝物が pnpm」と読め、CLAUDE.md の「pnpm はゴールではなく最新世代の題材」に反するため差し替えた。3 部を同格の light gray にし、青は矢印へ。宝石は積層ディスク(store の構造を示唆)に変更。

2 版目は Appendix を縦線で吊るしたが、線が Part II の底から出て「History の付録」に見えたため、3 版目で線を撤去し 2 段の独立レイアウトにした。

章番号(`Ch 1-4` など)は 1 ボックス 3 行になり組みが崩れやすいので入れていない。直後の Part 表が対応を示すので図には不要と判断。

### 図 1-1 4 つの登場人物(2026-08-30 / 標準 3:2)

`docs/basics/01-what-is-a-package-manager.md` — Developer / Package Manager / Registry / node_modules。

プロンプトは初版のまま変更なし。**Package Manager だけが青**だが、これは特定ツールの推しではなく「本書の主役は CLI ツール本体」を示すもので、本文の記述とも一致するため中立性の問題はない。

初版の生成結果は矢印が斜めに交差し、write 矢印が PM の枠から離れていた。再生成で直角配線になり、3 本すべてが PM を起点/終点として繋がる形になったので後者を採用。人物アイコンの描き込みも減り `simple geometric icons` に寄った。

node_modules だけ light gray の箱に入っていて 4 要素の視覚的な重みが揃っていないが、プロンプト指定どおりであり実害がないためそのまま採用。

### 図 1-2 4 つの仕事のパイプライン(2026-08-30 / ワイド 2:1)

`docs/basics/01-what-is-a-package-manager.md` — package.json → Resolve/Fetch/Link/Run Scripts → node_modules。

初版プロンプトは `Box 1 (blue, ...)` で Resolve だけが青塗りだった。4 工程は並列に対等なので、1 つ目だけ強調すると「Resolve が主役」と読める。0-1 と同じ構図の問題として同格の light gray に統一し、青は矢印へ。

工程番号 `1`〜`4` を各ボックスに入れた。本文が「解決・取得・配置・実行」の 4 つを順に節で解説するため、図の番号と本文の順序を対応させて行き来できるようにする狙い。

**本書で最初のワイド 2:1**。6 要素を横一列に並べるため 3:2 では文字が小さくなる。比率指定だけだと中央に小さく描かれることがあるので、LAYOUT に `spanning the full width of the canvas with even margins` を併記した。生成結果は 1774x887 でちょうど 2:1。

### 図 1-3 依存の依存がツリーに広がる(2026-08-30 / 標準 3:2)

`docs/basics/01-what-is-a-package-manager.md` — your-app → express → body-parser/debug/send → ms。

**your-app だけが青**だが、これは「あなたが書く 1 行」を指すもので中立性の問題はない。青い矢印 1 本と黒い矢印 4 本の対比が、本文の「1 行の宣言が数十個のインストールを意味する」を視覚で支える。

初版プロンプトは `declared` / `transitive` の浮遊タグ 2 個を置いていたが、どの要素を指すか曖昧で配置も不安定なため、矢印ラベル `you write this` 1 個に集約した。抽象語より「あなたが書くのはここだけ」の方が主張に直結する。`transitive` 側は矢印の色の対比で十分に読めるのでラベルを置いていない。

`ms` の枠を orange から light gray に変更。**オレンジは「問題・注意」の色**であり、ここは正常な推移的依存で警告ではない。

ツリーは階層がずれやすいので、LAYOUT で 4 列構成と各列のノード数・整列(ms は debug と同じ高さ)を明示した。

### 図 2-1 semver の 3 つの数字(2026-08-30 / 標準 3:2)

`docs/basics/02-package-json-and-semver.md` — 1.2.3 の各桁と MAJOR/MINOR/PATCH の対応。

**色分けは初版のまま残した**。オレンジ=MAJOR は「互換性を壊す=注意」で、オレンジを警告色として使う原則に合致する。青=MINOR、墨=PATCH と影響度の大きさが色の強さに対応していて理にかなっている。

変更点は 3 つ。`callout line`(斜め可)を各桁の真下への垂直線に変更し、箱を対応する桁の真下に中央揃えするよう明示した(0-1 で線の起点を曖昧にして失敗した反省)。また初版が使っていた `navy` はプリセット外の色なので `near-black` に修正。

生成結果は線が各桁と同じ色になった(指定外)が、対応関係が強まるのでそのまま採用。桁と箱の水平位置がわずかにずれているものの、垂直線があるので対応は明確に読める。

### 図 2-2 ^ と ~ が許す範囲(2026-08-30 / 標準 3:2)

`docs/basics/02-package-json-and-semver.md` — ^1.2.3 と ~1.2.3 の範囲を数直線で対比。

初版プロンプトは**下の行だけ目盛りを 2 つ**にしていた(1.2.3 と 1.3.0)。これだとバーが短いのか物差しが短いのか区別できず、比較図として機能しない。両行に同じ 3 目盛りを同じ位置で置かせ、**同一スケール上でバーの長さを比べられる**ようにした。

バーの終点は「〜の手前まで」という相対表現ではなく、「中央目盛りを覆う」「中央目盛りの手前で止まる」と**見た目の結果**で書くと生成が安定する。

オレンジの X は「そこには行かない=境界」を示すもので、警告色の使い方として妥当なので初版のまま残した。

### 図 2-3 dependencies の種類マップ(2026-08-30 / 標準 3:2)

`docs/basics/02-package-json-and-semver.md` — 4 種の dependencies を 2x2 で並べる。

初版の descriptor は `runtime` / `dev only` だったが、これは「実行時か開発時か」という軸に読める。**本文の区別軸は「誰の環境に入るか」**(利用者にも入る/自分の環境だけ)なので、`ships to users` / `your machine only` の対になる表現に変えて本文と揃えた。

アイコンを 4 つとも指定した(配送箱・レンチ・握手・疑問符)。2x2 の文字だけだと 4 つが均質に見えて区別が付きにくいため。二重支持の原則。

`dependencies` だけが青だが、これは 4 つの中で最も基本かつ頻度が高いためで中立性の問題はない。オレンジ枠は optionalDependencies の「失敗しうる」に対応していて警告色の使い方として妥当なので初版のまま残した。

懸念していた `optionalDependencies`(20 文字)は 1 行に収まった。

### 図 3-1 npm v2 と v3 の配置の対比(2026-08-30 / 標準 3:2)

`docs/basics/03-node-modules.md` — ネスト構造とフラット構造を左右で対比。

初版プロンプトは左右で名前がバラバラだった(右のルートが `flat`、3 箱が `A2` `B2` `C2`、左の重複が `C` と `C copy`)。これでは**別物の比較**に見えて、「同じ A・B・C が配置だけ変わる」という主眼が消える。左右とも `node_modules`、箱はすべて `A` `B` `C` に統一した。`flat` も `C copy` も実在しないフォルダ名で、その意味でも不適切だった。

オレンジは v2 側の 2 つの C にのみ。重複=解決すべき問題を示す。v3 側は解消後なので色を付けない。

なお、この図は D2(diagram-as-code)でも試作したが、左右パネルの高さが揃わず ELK/dagre のレイアウト調整に手間取った。ChatGPT 生成は一発で揃った。

### 図 3-2 hoisting とバージョン衝突(2026-08-30 / 標準 3:2)

`docs/basics/03-node-modules.md` — C v1 が hoist され、C v2 が B の下にネストする配置。

**矢印を落とした**。初版は `needs v1` / `needs v2` の 2 本を引いていたが、この図が答えるべき問いは「衝突したときどこに置かれるか」であって「誰が要求したか」ではない。依存グラフは直前の Mermaid が示しているので、この図は配置結果に専念させる。矢印を入れるとネストした C v2 から出る線が箱をまたいで交差し、構造が読めなくなる。

**1 回目の生成は塗りで作ったが差し替えた。**C v1 を青ベタ塗りにすると、A・B と同じ階層のはずなのに視覚的な重みが突出し、「C v1 だけ別物」に見えた。白背景+太い青枠に変え、C v2 も白背景+太いオレンジ枠にしたことで、3 つの箱が同格に見えつつ状態の違いが読める形になった。

タグは箱の上辺に食い込む形で生成されたが、浮遊させるよりどの箱に属するかが明確で良い。

### 図 3-3 幽霊依存(2026-08-30 / 標準 3:2)

`docs/basics/03-node-modules.md` — package.json は express しか宣言していないのに、app.js が debug を import できてしまう構図。

**警告三角形をやめた**。初版は debug の隣にオレンジの警告三角形を置いていたが、異常さは太いオレンジ枠と `not declared` タグで十分伝わる。三角形は要素が 1 つ増えるだけで、プリセットの `simple geometric icons` からも外れる。

`declares express` のタグを矢印ラベル `declares` に統合した。タグと矢印で同じ情報が二重になっていたため。

矢印は 2 本で色を分けた。`import debug` を青にしたのは、これがこの図で読ませたい主役の動線だから。`declares`(黒)との対比で「宣言した経路」と「宣言していない経路」が読める。

express の塗りも青ベタから白+細枠に変更(debug と同じ階層なので塗りを揃える。図 3-2 で確立した規則)。

なお下書き段階で A・B・C の抽象名で書きかけたが、**本文は express / debug という具体名で説明している**ため既存プロンプトの具体名を維持した。本文を確認せずに図を設計すると起きるズレ。

### 図 4-1 lockfile なしのズレ(2026-08-30 / 標準 3:2)

`docs/basics/04-lockfiles.md` — 同じ package.json から 1 月と 3 月で違うバージョンが入る。

**稲妻アイコン+`mismatch` を、テキスト `same package.json` に置き換えた**。食い違っていることは 1.2.3 と 1.3.0 という数字で既に見えている。図が足すべき情報は「**同じ package.json なのに**違う結果になった」という理不尽さで、それがこの章の問題提起そのもの。稲妻は「何か悪いことが起きた」以上を語らない。

オレンジ枠は Developer B 側だけ。後から入った人が違うものを掴む、という時間差の被害者を示す。

矢印ラベルは `install January` から `January` へ短縮(`install` は矢印の向きから自明)。

### 図 4-2 lockfile による再現性(2026-08-30 / 標準 3:2)

`docs/basics/04-lockfiles.md` — 同じ lockfile から local と CI が同じ結果を得る。

**4-1 と対になる構図**にした。4-1 はオレンジ枠で 1.2.3 と 1.3.0 が食い違い、4-2 は青枠で両方 1.2.3 が一致する。連続する 2 図なので、構図を揃えると「ロックファイルが入ると何が変わるか」が図同士の差分で読める。

初版の右端のブラケット(2 つの folder を繋ぐ縦の括弧)+ `identical` タグを、テキスト `same result` に置き換えた。装飾より言葉を置く教訓に従い、かつブラケットは 0-1 の縦線と同じく位置が不安定になりやすい。

箱のラベルは `node_modules` / `same tree` から両方 `1.2.3` へ。左右で名前が違うと別物に見える(3-1 の教訓)。**同じ結果になる**ことが主張なので同じ文字列を置く。

なお下書き段階で 4-1 の「1 月と 3 月」の構図を流用しかけたが、**本文のこの節の対比軸は local と CI**。3-3 に続いて本文未確認による設計ミスをしかけた。図を設計する前に必ず本文を読む。

生成結果は lockfile 側の矢印が 1 本から分岐する形になった(指定は 2 本)が、配線が整理されているのでそのまま採用。
